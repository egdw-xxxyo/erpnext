# Панель адміністрування (Ops Dashboard)

Невеликий вебзастосунок, який працює **поряд** зі стеком ERPNext на тому самому сервері й показує
його стан: здоров'я (health), версію, використання диска, останню резервну копію (backup), а також
дозволяє запускати розгортання (deploy), резервне копіювання та відновлення (restore) з живим
виводом консолі.

Адреса: `http://<host>:8081`. Вхід — **обліковий запис SSH цього сервера**.

---

## Чому окремий compose-проєкт

`./deploy build` виконує `docker compose -p docker up -d`, що перестворює **всі** контейнери
проєкту `docker`. Якби панель була сервісом у тому ж проєкті, розгортання, запущене з панелі,
знищило б контейнер, який транслює вивід цього самого розгортання.

Тому панель живе в окремому проєкті `ops` (`docker-compose.ops.yml`). Функція `dc()` у `./deploy`
жорстко прив'язана до `-p docker` — **не «виправляйте» це**, саме воно робить схему робочою.
`./deploy nuke` / `destroy` теж не чіпають том панелі.

## Чому команди виконуються через SSH

Панель не має ані docker-сокета, ані bind-mount репозиторію. Під час входу вона відкриває SSH-з'єднання
обліковими даними оператора, і **це з'єднання і є сесією**: усі команди й усі показники йдуть через
нього. Наслідки:

- панель не може зробити на сервері нічого, чого не міг би зробити сам оператор вручну;
- журнал аудиту (audit log) пишеться від імені оператора, тому власник файлу підтверджує запис;
- пароль ніде не зберігається — він існує лише під час виклику `connect()`.

## Встановлення на сервері

```bash
cd /home/mpa/git/erpnext
cp .ops.env.example .ops.env
sed -i "s|^OPS_SESSION_SECRET=.*|OPS_SESSION_SECRET=$(openssl rand -hex 32)|" .ops.env
# вкажіть OPS_ENV_LABEL=prod на проді та перелік дозволених користувачів
./deploy ops up
```

Панель **вмикається окремо на кожному хості**: без файлу `.ops.env` `./deploy` її просто не запускає.
Після цього `./deploy start|build|migrate|init` піднімають її автоматично, `./deploy stop` — зупиняє.

Керування вручну: `./deploy ops {up|down|rebuild|logs|status}`.

### Передумови на хості

| Що | Навіщо | Перевірка |
|---|---|---|
| `PasswordAuthentication yes` | вхід за паролем ОС | `sudo sshd -T \| grep passwordauth` |
| sshd слухає адресу docker-мосту | контейнер ходить на `host.docker.internal` | `ss -lntp \| grep :22` |
| вільний порт 8081 | публікація панелі | `ss -lntp \| grep 8081` |
| `jq`, `curl`, `python3` | збір показників | наявні у стоковій Ubuntu |

Якщо sshd слухає лише LAN-адресу — задайте `OPS_SSH_HOST=172.16.105.10x` у `.ops.env`.
Якщо ввімкнено `fail2ban`, додайте підмережу docker-мосту до `ignoreip`, інакше він конфліктуватиме
з власним блокуванням панелі.

## Що показує панель

| Панель | Джерело |
|---|---|
| Health | `curl /api/method/ping` через nginx, `mysqladmin ping`, `redis-cli ping` |
| Version | гілка / HEAD / тег / «брудне» дерево, останній Release Note, тег образу, `environment` із `site-config.json` |
| Disk | `df /`, `docker system df`, розмір журналу systemd; за кнопкою — том `sites` і `PJ-*.png` |
| Containers | `docker compose -p docker ps -a` |
| Backups | вміст `sites/<site>/private/backups`, згруповане за наборами |
| Jobs | останні 20 завдань із `.ops-jobs/` |

Усі панелі читають **один спільний знімок** із TTL 10 с, тож п'ять відкритих браузерів = один
SSH-виклик. Опитування зупиняється, коли вкладка неактивна.

## Дії (actions)

Панель ніколи не приймає рядок команди. Кожна дія — запис у фіксованій таблиці
`ops/app/commands.py` зі своїм валідатором аргументів; усе інше — 400.

| Дія | Команда |
|---|---|
| Update repo | `./updateRepo` |
| Deploy (build) | `./deploy build --silent` |
| Backup | `./deploy backup [--no-files]` |
| Restore | `./deploy restore <name> --yes` |
| Switch branch | `git fetch && git checkout <branch> && ./updateRepo` |
| Rebuild dashboard | `./deploy ops rebuild` |

Обмеження, які застосовуються ще до запуску:

- **одне завдання за раз** — блокування через `flock`, друге отримує «зайнято»;
- **`switch-branch`** відмовляє, якщо робоче дерево на хості має незакомічені зміни;
- **`build` на проді** заблоковано для комітів без тега (те саме правило, що й у `require_tag_on_prod`),
  але з поясненням замість миттєвої незрозумілої помилки;
- **`restore`** — двокрокове підтвердження: спершу показуються дата й розмір копії, потім треба
  ввести назву сайту вручну.

### Як виконуються довгі завдання

Завдання запускається через `setsid` у власній групі процесів, пише лог у
`.ops-jobs/<id>.log` на хості й одразу повертає ідентифікатор. Браузер читає лог через SSE
за байтовим зміщенням (`Last-Event-ID`).

Тому консоль **переживає**: перезапуск контейнера панелі (навіть спричинений самим завданням),
обрив SSH-сесії та закриття браузера. Стан завдання визначається за `kill -0 <pid>` і файлом
`.exit` — свідомо **не** через `pgrep -f "deploy build"`, бо цей шаблон збігається сам із собою.

## Резервні копії

`./deploy backup` типово робить копію **разом з файлами** (`--with-files`) і лишає останні
`OPS_BACKUP_KEEP` (типово 5) наборів.

> **Місце на диску.** Набір з файлами — це ~2.7 ГБ, з яких ~2.5 ГБ — це `PJ-*.png`
> (рендери етикеток, які відтворюються). П'ять таких наборів ≈ 13.5 ГБ на тому ж диску,
> де `./deploy build` потребує 8–10 ГБ вільного місця. Захист: `backup_space_guard` не дасть
> почати копіювання, якщо місця не вистачить, а очищення старих копій відбувається **до**
> створення нової. На проді варто спершу почистити `PJ-*.png`:
> `find sites/frontend/private/files -maxdepth 1 -name 'PJ-*.png' -mtime +30 -delete`
>
> Альтернатива: `./deploy backup --no-files` (лише БД, ~24 МБ) і `--keep=N`.

Команди з консолі сервера:

```bash
./deploy backup                      # з файлами, лишити OPS_BACKUP_KEEP наборів
./deploy backup --no-files           # лише база даних
./deploy backup --keep=3
./deploy backup --prune-only --keep=1
./deploy restore --list
./deploy restore 20260814_174115-frontend          # спитає назву сайту
./deploy restore 20260814_174115-frontend --yes    # без запиту (так робить панель)
```

`restore` спершу знімає **страхувальну копію** поточного стану, потім відновлює, і обов'язково
виконує `bench migrate`, `clear-cache`, `ensure_assets_manifest`, `fix_assets` — без цього
відновлена база несе старий `assets.json`, і nginx віддає HTML замість CSS.

## Журнал аудиту

`.ops-jobs/audit.log`, по рядку JSON на подію (вхід, невдалий вхід, запуск дії, підтвердження
відновлення), запис під `flock`. Переглядається на `/audit`.

> **Обмеження.** Поки всі заходять як `sergadm`, журнал фіксує реальні дії та час, але одну
> особу. Щоб «хто саме запустив» мало сенс, кожному операторові потрібен власний обліковий запис
> ОС у групі `docker` із правом запису в репозиторій.

## Безпека

Панель доступна в локальній мережі по **HTTP без шифрування** — це свідоме рішення, тож пароль
іде мережею у відкритому вигляді. Що зроблено натомість:

- обмеження спроб входу: 5 невдач на пару (користувач, IP) за 15 хв → блок на 15 хв; плюс
  глобальна межа 20 невдач/хв;
- список дозволених користувачів перевіряється **до** спроби SSH, тож чужий логін не доходить до sshd;
- ключ хоста фіксується при першому підключенні (TOFU), далі перевіряється;
- CSRF-токен на кожній змінювальній дії, cookie `HttpOnly` + `SameSite=Strict`;
- сесія живе 1 год і 30 хв без активності, після чого SSH-з'єднання закривається.

## Розробка

```bash
cd ops
python3 -m venv .venv && .venv/bin/pip install -r requirements.txt
OPS_SESSION_SECRET=dev OPS_SSH_HOST=172.16.105.103 OPS_REPO_PATH=/home/mpa/git/erpnext \
  OPS_ALLOWED_USERS=sergadm OPS_DATA_DIR=/tmp/opsdata \
  .venv/bin/uvicorn app.main:app --reload --port 8081
```

Запускати локально краще **не в контейнері**: на macOS немає `setsid`, `flock` і `tail --pid`,
тож перевірити там можна лише збірку образу, вхід і панелі — не механізм завдань.

`--workers 1` обов'язково: SSH-з'єднання й сесії живуть у пам'яті процесу.
