# Резервний сервер (дзеркало)

Якщо зв'язок з основним сервером ERPNext зникає, роботу можна продовжити на **дзеркалі** — окремому
Linux-комп'ютері в локальній мережі, який постійно тримає актуальну копію бази даних і файлів.
Коли основний сервер повертається, усе, що зробили на дзеркалі, переноситься назад, а дзеркало знову
переходить у режим очікування.

Одночасно дані приймає **лише один сервер**. Зміни двох серверів не зливаються: під час повернення
база основного сервера **замінюється** базою дзеркала.

## Як це працює

| Що | Як |
|---|---|
| База даних | Реплікація MariaDB (GTID) з основного сервера. Відставання — секунди. |
| Канал | SSH-тунель із дзеркала на основний сервер (`mirror-tunnel`). Порт БД основного сервера відкритий лише на `127.0.0.1`. |
| Файли (вкладення) | `rsync` кожні `MIRROR_FILES_INTERVAL` секунд (`mirror-files`). PNG-рендери етикеток `PJ-*.png` не копіюються. |
| Код | Дзеркало збирає образ із того самого коміту, що й основний сервер (`./deploy mirror sync-code`). |
| Застосунок на дзеркалі | Зупинений, поки дзеркало в очікуванні. `./deploy start/build/migrate/init/restore` заблоковані. |

Стан дзеркала зберігається в `.mirror/` (не в git): `state` (`standby` / `active`), `primary-commit`,
`built-commit`, `files-ok`.

## Налаштування

### 1. Основний сервер

```
cp .mirror.env.example .mirror.env
# MIRROR_ROLE=primary, MIRROR_REPL_PASSWORD=<пароль без лапок>
./deploy build --silent          # БД перезапускається з бінарним журналом
./deploy mirror primary-setup    # створює обліковий запис реплікації
```

Бінарний журнал зберігається 2 дні. Перевіряйте вільне місце: `./deploy mirror status` показує його розмір.
Якщо дзеркало було відключене довше за 2 дні, реплікація не відновиться — запустіть
`./deploy mirror setup` на дзеркалі ще раз.

### 2. SSH-доступ із дзеркала

- Створіть ключ на дзеркалі: `ssh-keygen -t ed25519 -f ~/.ssh/erp_mirror -N ""`.
- Додайте публічний ключ у `~/.ssh/authorized_keys` користувача основного сервера, який входить у групу
  `docker` і може запускати `./deploy`.
- У `sshd_config` основного сервера має бути дозволено `AllowTcpForwarding yes`.

### 3. Дзеркало

```
git clone <repo> && cd erpnext && git submodule update --init
cp .mirror.env.example .mirror.env
# MIRROR_ROLE=replica, MIRROR_PRIMARY_SSH, MIRROR_PRIMARY_SSH_KEY, MIRROR_PRIMARY_REPO, пароль реплікації
./deploy mirror setup       # копія БД + файлів, запуск реплікації (довго)
./deploy mirror sync-code   # збирає образ із коміту основного сервера
./deploy mirror status
```

У `status` має бути `Slave_IO_Running: Yes`, `Slave_SQL_Running: Yes`, невелике `Seconds_Behind_Master`
і однаковий код основного сервера та дзеркала.

Після **кожного** релізу на основному сервері запускайте на дзеркалі `./deploy mirror sync-code`
(або додайте його в cron раз на ніч). Зміни схеми БД приходять реплікацією, але код має збігатися.

## Аварія: перехід на дзеркало

```
./deploy mirror start
```

Команда:
1. відмовляє, якщо основний сервер доступний по SSH (щоб користувачі не працювали у двох базах одночасно;
   якщо сервер доступний, але несправний — `--force`);
2. відмовляє, якщо код дзеркала відрізняється від коду основного сервера (`--force` — під вашу відповідальність);
3. від'єднує БД від реплікації і дозволяє запис;
4. запускає ERPNext.

Далі користувачі відкривають `http://<IP дзеркала>:8080`, а в застосунку Android змінюють адресу сервера
в налаштуваннях.

Поки дзеркало працює, воно кожні 30 секунд перевіряє основний сервер. Щойно той стає доступним,
дзеркало **ізолює** його (`./deploy mirror fence` на основному сервері): зупиняє nginx, воркери
й планувальник і блокує `./deploy start/build/migrate`. Так користувачі не почнуть випадково писати в стару базу.

## Повернення на основний сервер

```
./deploy mirror failback
```

1. Ізолює основний сервер (якщо ще не ізольований).
2. Переводить дзеркало в режим обслуговування і зупиняє воркери.
3. Робить резервну копію БД дзеркала, копіює її та нові файли на основний сервер.
4. Відновлює її на основному сервері через `./deploy restore` — той спершу робить власну страхувальну
   копію бази, якою вона була до аварії.
5. Знімає ізоляцію з основного сервера.
6. Зупиняє застосунок на дзеркалі і заново налаштовує реплікацію.

Якщо команда зупинилася з помилкою до кроку 5, основний сервер лишається ізольованим, а дзеркало —
у режимі обслуговування: усуньте причину і запустіть `failback` ще раз.

Користувачі повертаються на звичну адресу, Android — на адресу основного сервера.

## Що не переноситься

- Черги фонових завдань (Redis) на момент аварії.
- Вхідні вебхуки WhatsApp і пошта: вони адресовані основному серверу і під час аварії губляться.
- Файли, завантажені на основний сервер за останні `MIRROR_FILES_INTERVAL` секунд перед аварією
  (запис у БД буде, файлу — ні).
- `PJ-*.png` — вони генеруються заново.
- Застосунки з `apps.json` збираються з гілок, а не з точного коміту: після змін у форках запускайте
  `sync-code` на дзеркалі.

## Ручне скасування

Якщо дзеркало вийшло з ладу, а зміни на ньому не потрібні, на основному сервері:

```
./deploy mirror unfence
```

Усе, що зробили на дзеркалі, буде втрачено.
